# Experimental five-direction face enrollment

Vendor manual V2.67 printed pages 9–10 and 60–62: 0x13 uses a 35-byte payload (admin, 32-byte name, direction, timeout) and success returns 2-byte UID plus accumulated five-bit orientation mask. The 0x1D ordinary face/palm enrollment is unchanged. The PC tool uses 0x1D, not this experimental sequence.

The door package exposes a button and API action enroll_face_directions, with progress in the existing enrollment result entity. Requires a complete refreshed user directory and a new face name (a palm with the same name is permitted). Five explicit requests use 01, 04, 02, 10, 08; 25 s per direction and 1.2 s between confirmed steps. The first request follows reset; later requests deliberately avoid reset to preserve module context. The expected cumulative masks are 01,05,07,17,1F. All replies must have the same new face UID in 1..1000 and exactly the expected mask. No fallback to duplicate registration, no retry and no disabling duplicate detection. Completion emits one enrollment-success event, refreshes the directory, and resumes prior continuous recognition after successful refresh according to existing settings.

On rejected command, timeout, malformed mask, changed UID or cancellation, abort and leave recognition stopped. The firmware may already have stored a partial user; review the actual directory and manually delete only the intended test record if necessary before restarting. No automatic deletion or claim of rollback. Do not test as the sole access method on an occupied door. No physical validation of 0x13 or same-UID continuation on v2.30-QRXF-PV yet. If this firmware returns per-direction rather than cumulative masks or requires a combined mask, collect the reply and revise after confirmation.
