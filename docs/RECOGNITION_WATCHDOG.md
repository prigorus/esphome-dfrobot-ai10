# Continuous recognition watchdog

The compact door package arms the desired continuous recognition state at boot before user-directory refresh. Slow or failed initialization must not permanently lose that request. Explicit start/stop and one-shot verification change the desired state; a temporary capture reset does not. A failed or cancelled five-direction enrollment deliberately clears the request until the operator inspects partial enrollment. Existing normal enrollment and configuration actions are not automatically repeated.

The main loop checks the requested state every 10 seconds when no incompatible operation is running. Recovery is RESET (0x10), then STATUS (0x11), require successful idle (0), then a fresh VERIFY with the desired timeout/attempt settings. The first three attempts are separated by 1.5 s, then delays of 60, 120, 240 and 300 s, capped at five minutes; attempts continue until a valid VERIFY result or explicit stop. Recovery is inhibited throughout the camera capture/restart cycle, guided enrollment, directory requests and other pending commands. No watchdog path synthesizes recognition success. FULL mode retains its per-request host timeout and normal cycle repetition. ECO may be silent legitimately; after 10 minutes without a valid verification result the session is proactively renewed. This introduces a short planned interruption in ECO, not a proof of module failure. No automatic power cycling.

The existing ai10_recognition_recovery substitution controls recovery and watchdog, defaults true in the door package. A new diagnostic text sensor Stanje prepoznavanja indicates requested/operation/recovery states, not proof of actual camera recognition. Logs report command failures and retry scheduling without biometric data. The separate intent is RAM-only; the door package intentionally starts automatically on a new ESP32 boot. Persistent sensor hardware failure or a UART fault still requires repair. No overnight hardware test has been performed.

2026-11-27 follow-up: pending recovery backoff is an idle wait, not an active UART transaction. Explicit commands and user-directory refresh may supersede this wait. Active reset/status/transfer operations still exclude new commands. Queued directory refresh has priority over idle backoff to avoid mutual blocking. The continuous intent is preserved unless explicitly stopped or a guided enrollment fails. Hardware confirmation pending.
