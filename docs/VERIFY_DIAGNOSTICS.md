# Verification diagnostics

2026-11-27 hardware log: an empty database returned 0x08 repeatedly (roughly every 0.2–0.4 seconds) after a single FULL request. A quiet-window guard was added in 48a5689, but the operator subsequently reported that neither recognition nor enrollment worked. The guard has therefore been withdrawn: the original configured fixed repeat interval is restored. Late VERIFY replies during that interval are ignored and counted for diagnostics. There is no forced reset caused by continuing late replies. This does not guarantee identification of stale packets arriving after a subsequent request; the protocol has no transaction ID. Do not treat duplicate suppression as proof of liveness or authorization.

NOTE 0x01 is decoded as eight signed little-endian fields following the note ID. Raw observed 01 01 00 FC 00 76 01 B2 01 78 02 ... yields state 1, rectangle [252,374,434,632]. Manual V2.67 state table: 0 normal face, 1 no face, 128 palm detected; bounding box alone is not proof of detection. The legacy is_face_detected getter still means normal face OR palm, with separate is_palm_detected. NOTE never authorizes.

INFO logs show accepted VERIFY result, elapsed milliseconds, source sensor/host and UID only on validated success. The separate diagnostic text sensor retains the last accepted result, rather than reset/status or directory replies overwriting it. 0x1C remains undocumented. No images, templates, names or QR contents added to these logs. Physical confirmation and multi-direction recognition tests remain pending. No new firmware log was available when reverting the quiet-window guard; the underlying recognition/enrollment failure is not established.
