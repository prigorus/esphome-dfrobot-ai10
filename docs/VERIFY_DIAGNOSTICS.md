# Verification diagnostics and reply drain

2026-11-27 hardware log: an empty database returned 0x08 multiple times (roughly every 0.2–0.4 seconds) after a single FULL request. Previously a 1 s fixed gap could send the next request while those replies were still arriving. FULL now waits for both configured minimum delay and 750 ms without another VERIFY reply, with a parser/receive-buffer idle check. Late replies within this gap cannot trigger callbacks or increment the failed capture count. Persistent replies beyond the configured minimum delay plus 5 s trigger the existing reset/status recovery. The watchdog and manual stop remain in control. This is a conservative temporal guard, not a transaction ID: firmware can still send stale replies after a later request. No biometric validation rules changed. ECO uses the existing continuous logic.

NOTE 0x01 is decoded as eight signed little-endian fields following the note ID. Raw observed 01 01 00 FC 00 76 01 B2 01 78 02 ... yields state 1, rectangle [252,374,434,632]. Manual V2.67 state table: 0 normal face, 1 no face, 128 palm detected; bounding box alone is not proof of detection. The legacy is_face_detected getter still means normal face OR palm, with separate is_palm_detected. NOTE never authorizes.

INFO logs show accepted VERIFY result, elapsed milliseconds, source sensor/host and UID only on validated success. The separate diagnostic text sensor retains the last accepted result, rather than reset/status or directory replies overwriting it. Host malformed reply/timeout is distinct from a sensor-reported result; recovery reset failures also update the diagnostic. 0x1C remains undocumented. No images, templates, names or QR contents added to these logs. Physical confirmation and multi-direction recognition tests remain pending.
